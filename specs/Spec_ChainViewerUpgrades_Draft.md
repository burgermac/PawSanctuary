# PawSanctuary — Chain Viewer Upgrades

**Status: DRAFT, 18 Nov 2026. Not started, not scheduled.** Written cold from a read of the code the same day, to carry out the second half of decision **D13** (`PawSanctuary_Alignment_Plan.md`). Not yet reviewed by the design authority. Three tasks, one per session, in the order below.

**Self-contained brief.** Assumes no prior conversation. Everything it relies on was read in the code on 18 Nov 2026; line numbers drift, so search by name.

---

## 0. What this is, and what it is not

`MergeProgressionView` (the chain viewer, opened by the "i" button on the board's info bar) currently lists every tier of a chain: art, name, "Tier N of M", a star on the top tier. It holds no state, no view model and no knowledge of what the player owns.

This spec adds three things to it, all derived live, **none persisted**:

1. **Owned-count badges** on tiers the player holds.
2. **A buy shortcut** on any tier the Dog Tag Item Store currently stocks.
3. **A "Generated by" line**, only if the lookup is cheap (§5).

**No save change.** No new persisted field, so no schema bump, migration or `PersistenceTests` case (CLAUDE.md rule 4 is not triggered). If a task turns out to need persisted state, stop: that is the held first-discovery collection (D13 part 1) and is out of scope.

### Constraints inherited from recorded decisions

| Decision | What it means here |
|---|---|
| **D13** | No `?` slots, no discovered/undiscovered state, no first-discovery reward. The viewer keeps showing every tier. |
| **D7** | The buy shortcut is a monetization surface. It appears only when `isMonetizationUnlocked` (`commerce.hasReachedFirstWall && playerLevel >= monetizationUnlockLevel`). The badges and the footer are not monetization and show always. |
| **D12** | A bought item does not credit an order. Nothing in the viewer's copy may suggest a purchase fills an order. The viewer is not order-aware and stays that way. |
| **D9** | Prices and stock are not tuned to make the shortcut convert. The viewer reads the store as it is. |
| **D3** | The store is the release valve for a player blocked on one item; this is the contextual path to it, not a new sink. |

### Out of scope

- Any first-discovery state, `?` placeholders, "new" markers or discovery rewards (D13 part 1).
- Changing store stock, prices, rotation, the reroll, or adding stock rules for the viewer.
- Buying for a specific order, highlighting tiers an order wants, or any order awareness.
- Per-tier producer information for tiers reached by merging (§5).
- A grid redesign of the viewer. The list layout stays.
- New currencies, IAP, or a new Dog Tag faucet.
- New telemetry. `PlaytestMetrics` is untouched.

## 1. Where things are (verified in code, 18 Nov 2026)

- **Viewer:** `private struct MergeProgressionView: View` in `MergeBoardView.swift`. Takes `chainID: String` only. Presented through `SheetRoute.mergeProgression(String)` (the `routeContent` switch). The "i" button sits in the info bar and appears when `selectedItemInfo.chainID != nil`, so the viewer opens for **any** chain category, not only animals.
- **Store:** `DogTagStore` (`DogTagStore.swift`), `slots: [DogTagStoreSlot]`. A slot is `{ id, chainID, tier, priceDogTags, purchased }`. Three slots, rotating daily, stock one each. `makeStock` draws from **unlocked animal chains only**, tiers `deepest − 4 … deepest − 1`. Slots are (re)built by `viewModel.refreshDogTagStore()`, which `DogTagStoreSection` calls on appear.
- **Purchase path:** `MergeBoardViewModel.purchaseDogTagStoreSlot(_:) -> Bool`. Refuses if sold or unaffordable; places the item via `placeOrBankItem` (board, else inventory, else an `.inventoryFull` toast and no charge); deducts Dog Tags; records the spend; marks the slot sold; persists. Clamps the tier to the chain's `maxTier`.
- **Store UI today:** `DogTagStoreRow` in `ShopView.swift`. Shows a price button, greyed when unaffordable, "Sold" when bought. `ShopView` is itself only reachable once `isMonetizationUnlocked` is true.
- **What the player owns, three existing definitions, none of which is right for a badge:**
  - `boardTaskCensus`: board only, unlocked cells, excludes bubbled items. Deliberately excludes inventory (hand-in tasks want board pressure).
  - `mergeReadyKeys`: board **plus** inventory, includes bubbled. Used for merge hints.
  - Order credit: not a census at all (D12).

## 2. Task 1 — Owned-count badges

**Goal.** On each tier row, show how many of that tier the player holds right now.

**Definition (a fourth, named on purpose).** *Owned* = items on unlocked board cells that are not bubbled, **plus** items in the animal inventory (`inventory`). Same bubble reasoning as `boardTaskCensus` (an item still encased is not yet the player's); inventory included because someone looking at "what do I have" expects a banked item to count. Power-up inventory, materials and producers are not counted: they are other categories and the viewer's chain is the one selected.

**Changes.**
1. Pass the view model into the viewer: `MergeProgressionView(chainID:, viewModel:)`, updated at the `routeContent` call site. The view model is `@Observable`, so counts update while the sheet is open.
2. Add one computed property on the view model, `ownedItemCounts: [ChainTierKey: Int]`, following the shape of `boardTaskCensus`. Compute it once per render, not per row (the same reasoning as `dailyTaskHighlights`).
3. In each tier row, when the count for `(chainID, index)` is above zero, show a small count pill ("×2") over the art's corner. **Nothing when the count is zero:** no "×0". The top-tier star stays.
4. Accessibility: the row's label gains "you have N".

**Done when:** a banked item and a board item both count; a bubbled item does not; a tier the player does not hold shows no badge; the badge ticks up live if an item arrives while the sheet is open.

**Tests** (`ChainViewerTests.swift`, new; build the view model the way `OrderFulfilmentRuleTests.makeViewModel()` does, including `vm.boardState.recalc()`): board item counts; inventory item counts; bubbled item excluded; other chain and other tier excluded; empty board gives an empty map.

## 3. Task 2 — Buy shortcut ("See in store")

**Interpretation to confirm.** D13 calls this a "See in store" shortcut and requires it to route through `purchaseDogTagStoreSlot`. A button that merely navigates to the shop would not use that path, so this spec reads it as a **direct buy**: the tier row shows the store's price and one tap buys it, exactly as `DogTagStoreRow` does. If the owner wants navigation to the Item Store instead, the change is one line (open `.shop` rather than call the purchase), and the gating and tests below still hold.

**Changes.**
1. View-model helper `chainViewerStoreSlot(chainID:tier:) -> DogTagStoreSlot?`. Returns `nil` unless `isMonetizationUnlocked`, and nil if the store has no slot for that chain and tier. Otherwise returns the slot, **including a sold one**, so the row can say "Sold" rather than silently losing the button mid-session.
2. The viewer calls `viewModel.refreshDogTagStore()` on appear (the same idempotent call the store section makes), so a day-old shelf is not shown.
3. A tier row with a slot shows a caption "In today's Item Store" and a price button matching `DogTagStoreRow`: tag icon and price; greyed if `dogTags < priceDogTags`; "Sold" if `purchased`. Tapping calls `purchaseDogTagStoreSlot(slot)`. **That function is the only thing the button calls.**
4. If the purchase returns false (no room, so the `.inventoryFull` toast fires), nothing changes and nothing is charged. No extra handling.
5. The viewer stays open after a purchase; the owned badge from Task 1 ticks up, which is the confirmation.
6. Chains the store never stocks (supplies, materials, tools, sub-objects) simply never have a slot, so they show nothing. No special case.

**Copy rule (D12).** The caption and button must not mention orders, "fill", "deliver" or "complete". The caption says where the item is sold, nothing about what it is for.

**Done when:** before the D7 gate the viewer shows no price anywhere; after it, a stocked tier shows its price, a purchase puts the item on the board (or inventory), debits the exact slot price once, flips the row to "Sold", and `SpendQuotaDailies`' spend counter moves as it does for a Shop purchase.

**Tests:**
- helper returns nil before the D7 gate and the slot after it (`unlockMonetizationForTesting()` is the existing DEBUG helper; tests build Debug);
- helper returns nil for a chain/tier the store does not stock, and the sold slot (not nil) after purchase;
- purchasing through the viewer's path debits once and marks sold;
- **D12 guard:** with an open order wanting the exact bought chain and tier, buying leaves the order uncredited. `OrderFulfilmentRuleTests` already pins the underlying rule; this adds the viewer's route to it so a future "smart" shortcut cannot bypass `purchaseDogTagStoreSlot`.
- Mutation-check each new test (break the thing it guards, see it fail, restore), as was done for the D12 tests.

## 4. Why Task 2 is not simply "navigate to the shop"

D13 names two reasons for it, restated so the task is judged against them: it is the contextual buy path the Parity Audit lists as partial (row 39), and it serves D3's conversion reasoning, which the D12 check found the random daily shelf serves only loosely, because the shelf offers three random tiers whether or not they match anything the player wants. The viewer is the one place the player has already picked a specific item. Showing the store's price there does not change what the store sells (D9); it only makes an existing offer findable from where the player is looking.

## 5. Task 3 — "Generated by" footer (conditional)

D13 adopted this **only if a chain-to-producer lookup is cheap**, and said that had not been checked. What this read found, still not a proof:

- A family spawner records its species and exposes `ProducerTile.animalChainID`, so animal chains map to a family spawner by species.
- The supply boxes (`groomingBox`, `feedBox`, `shelterBox`) are documented as producing the three `supply.*` chains at tier 0.
- That is a reverse lookup over tables that already exist, but display names for producers were not confirmed.

**Step 3.0 is a go/no-go.** Confirm that a chain-to-producer display name can be had from existing data without adding a table. If it needs a new table, **stop and drop this task**; D13 made it optional for exactly that case.

**If it goes ahead, one honest limit applies.** Only tier 0 is *generated*. Higher tiers are reached by merging, and generator-tier progression (Task 2.3) can make a producer emit above tier 0. The reference's footer is per item, and how it treats a merged tier was not captured. So show the line **once per chain, under the title**, as "Made by: <producer>", and not per tier. Chains with no producer (powerUp, currency, materials) show nothing.

**Done when:** an animal chain and a supply chain each show the right producer; a chain with none shows no line; no table was added.

## 7. Defaults chosen that the owner may want to change

- Owned includes inventory and excludes bubbled items (§2).
- The shortcut is a direct buy, not navigation (§3).
- A sold row stays visible as "Sold" rather than disappearing (§3).
- The viewer stays open after a purchase (§3).
- The footer is per chain, not per tier (§5).
