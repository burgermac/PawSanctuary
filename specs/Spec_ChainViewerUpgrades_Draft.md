## 0. What this is, and what it is not

**In plain language.** Tapping the small "i" next to an item's name opens a list of every step of that item's chain. Since PR #115 the list also shows how many of each step you have (a small "×2" badge). This spec adds two more things: a way to buy a step that today's Item Store is selling, right from that list, and one line saying which spawner makes the chain ("Made by: Scratching Post").

**What changed since the first draft.** When this spec was first written, a bought item could never fill an order (D12). Under **D14** it can: if you buy an item an order wants, and it lands on the board, that order's slot lights up, and once every slot is lit the **Deliver** button appears. The shortcut is therefore now a real way to finish an order you are one item short of, which is the reason D3 gave for selling items at all. It also means a few rules below changed, and one owner question (CV-1) needs an answer before Task 2.2 starts.

All three additions are derived live; **none is persisted**. **No save change**: no new persisted field, so no schema bump, migration or `PersistenceTests` case (CLAUDE.md rule 4 is not triggered). If a task turns out to need persisted state, stop: that is the held first-discovery collection (D13 part 1) and is out of scope.

## 1. Where things are (verified in code, 22 Nov 2026)

- **Viewer:** `private struct MergeProgressionView: View` (`MergeBoardView.swift:1748`). Takes `chainID` and, since #115, `viewModel` (`:1749-1750`). Reads `viewModel.ownedItemCounts` once per render (`:1756`) and shows a "×N" pill on held tiers (`:1774-1785`). Presented by `.sheet(item: $activeRoute)` (`:349`) through `SheetRoute.mergeProgression(String)` (`:1729`, routed at `:808-809`). The "i" button (`:1094`) appears whenever the selected item has a chain (`selectedItemInfo`, `MergeBoardViewModel.swift:704-735`), so the viewer opens for **any** chain category: animals, supplies, sub-objects, currency, toolbox, wildcard.
- **Store:** `DogTagStore` (`DogTagStore.swift`). `slots: [DogTagStoreSlot]`; a slot is `{ id, chainID, tier, priceDogTags, purchased }` (`AnimalSpecies.swift:1815-1821`). Three slots (`dogTagStoreSlotCount`, `AnimalSpecies.swift:2296`), one of each, rotating daily (`rotateIfNeeded`, `DogTagStore.swift:30-35`). `makeStock` (`:49-75`) draws from **unlocked animal chains only**, tiers `deepest − 4 … deepest − 1` (`AnimalSpecies.swift:2297-2298`), chain picked at random per slot. Price is `15 + 18 × (tier − cheapest tier)` (`DogTagStore.swift:83-85`; `AnimalSpecies.swift:2301-2302`), so 15 / 33 / 51 / 69 Dog Tags. Slots are (re)built by `viewModel.refreshDogTagStore()` (`MergeBoardViewModel.swift:1932-1935`), which `DogTagStoreSection` calls on appear (`ShopView.swift:286`). A paid reroll costs 5 (`paidRefreshDogTagStore`, `MergeBoardViewModel.swift:1941`).
- **Purchase path:** `purchaseDogTagStoreSlot(_:) -> Bool` (`MergeBoardViewModel.swift:1956-1971`). In order: refuses if sold or unaffordable (`:1957-1958`); clamps the tier to the chain's `maxTier` (`:1959-1960`); places the item with `placeOrBankItem` and refuses, **charging nothing**, if that fails (`:1962`); deducts the Dog Tags (`:1963`); records the spend through `updateAllAfterSpend(kind: .dogTags, …)` (`:1964`, which feeds `quests.updateQuestsAfterSpend`, `:3226-3228`, `QuestCoordinator.swift:221`, the D6 spend counter); marks the slot sold (`dogTagStore.markPurchased`, `:1965`; `DogTagStore.swift:90-93`); persists (`:1968`).
- **Full board:** `placeOrBankItem` (`MergeBoardViewModel.swift:2147-2156`) puts the item on a random empty unlocked cell; if there is none, into storage (`inventoryStore.addItem`); if storage is full too, it shows the `.inventoryFull` toast (`:2154`) and returns false, so the purchase charges nothing. **Under D14 an item that went to storage does not count for an order** until the player places it (pinned: `OrderFulfilmentRuleTests.testAPurchaseBankedToStorageBecauseTheBoardIsFullDoesNotCount`, `OrderFulfilmentRuleTests.swift:202`).
- **Order rule today (D14, built in tasks 1.3–1.5):** `AdoptionOrder.heldState(census:)` (`AnimalSpecies.swift:1152-1166`) reads the live `boardTaskCensus` (`MergeBoardViewModel.swift:747-754`: unlocked cells, bubbled items excluded, **storage excluded**). `orderHeldState(at:)` (`:3813-3816`); delivery only via `deliverOrder(id:)` (`:3856`). A store purchase of the wanted item makes the slot held without paying anything (`OrderFulfilmentRuleTests.testAStorePurchaseOfTheWantedItemMakesTheSlotHeld`, `:188`).
- **Store UI today:** `DogTagStoreRow` (`ShopView.swift:318-366`): one tap on the price button calls `purchaseDogTagStoreSlot` (`:345`), **no confirm step**; greyed when unaffordable, "Sold" when bought. The Item Store is the second section of `ShopView`, below the balance line, a sound toggle and the generator section (`ShopView.swift:21-51`).
- **How the shop is reached:** only through `activeRoute = .shop`, from the HUD cart button, itself shown only when `isMonetizationUnlocked` (`MergeBoardView.swift:644-645`), and from the Reward Ladder tray tile, gated on `isRewardLadderAvailable` = the same gate (`TaskTrayView.swift:585-598`; `MergeBoardViewModel.swift:411`). `SheetRoute.shop` carries no payload (`MergeBoardView.swift:1725`), and `ShopView` takes no "focus" argument and has no `ScrollViewReader` (`ShopView.swift:9-20`). The viewer has no access to `activeRoute` (it receives only `chainID` and `viewModel`).
- **What the player owns, four definitions:**
  - `boardTaskCensus` (`MergeBoardViewModel.swift:747`): board only, unlocked cells, bubbled excluded. **Orders and daily hand-in tasks** use it.
  - `ownedItemCounts` (`:767-777`): board **plus** storage, bubbled excluded. **The viewer's badges** use it (Task 2.1).
  - `mergeReadyKeys`: board plus storage, bubbled included; merge hints.
  - The old D12 "order credit" counter is gone; `OrderLine.fulfilled` is now set only on delivery.

## 2. Task 2.1 — Owned-count badges (done)

Built as specified in the first draft and merged as PR #115. *Owned* = unlocked board cells, not bubbled, **plus** storage (`ownedItemCounts`, `MergeBoardViewModel.swift:767`). Pill "×N" over the art's corner, nothing at zero, accessibility label gains "you have N" (`MergeBoardView.swift:1774-1785`, `:1809-1811`). Tests: `ChainViewerOwnedCountTests` (six cases, `:44-90`).

**One consequence of D14 to know about (not a bug in 2.1).** The badge counts storage; orders do not. A player can see "×1" on a tier while the order wanting it stays unlit, because that one copy is in storage. This was a deliberate choice in 2.1 ("what do I have" should include a banked item) and is left as is; §3.3 step 5 handles the one case where this spec creates it (a purchase that goes to storage). If the owner would rather the badge match orders, that is a one-line change to `ownedItemCounts` plus its tests, and a separate task.

## 3. Task 2.2 — "See in store" shortcut

### 3.1 Owner decision CV-1: what does tapping it do?

This was raised as **Q17** in `PROJECT_STATE.md` ("Decisions waiting"), where the project manager recommended **navigation**. It is restated here with what has been learned since, because the evidence and the cost picture changed.

**Option A — Buy directly from the viewer. Recommended.** A tier the store is selling today shows the store's price on its row ("In today's Item Store" and a tag-price button, the same look as `DogTagStoreRow`). One tap calls `purchaseDogTagStoreSlot`, exactly as the shop row does.
- *For:* the player buys the thing they are looking at, without a screen change, and then sees the badge tick up as confirmation. Smallest build (a ~10-line helper on the view model and one button in the row), entirely unit-testable, no new navigation. Under D14 the bought item can now be the last slot of an order, so this is the moment D3 describes. It is no riskier for accidental spending than the shop itself, whose row is also one tap with no confirm (`ShopView.swift:343-345`), and at most three rows of the viewer can ever carry a button.
- *Against:* the reference button is labelled "SEE IN STORE", which reads as navigation, and in Travel Town the store screen followed the viewer (below). It adds a second place where Dog Tags can be spent on a store slot (the *path* stays one function, but there are two buttons). The player does not see the other two slots or the 5-tag reroll on the way.
- *Variant:* add a confirm step ("Buy Pup for 33 Dog Tags?"). Cheap, but the shop row has none, so the two would behave differently. Not recommended unless the owner wants it.

**Option B — Open the Item Store with that item in view.** The tier row shows the same price; tapping it closes the viewer and opens the shop scrolled to the Item Store, with that slot highlighted. The player buys there as usual.
- *For:* matches the reference label and what Travel Town appears to do; every purchase still happens on one screen; the player sees the whole store (the other slots, the reroll, the wildcard). This was the PM's Q17 reasoning, and it is sound.
- *Against:* noticeably more work than the first draft said. The first draft called it "one line"; it is not: the viewer cannot reach `activeRoute`, `SheetRoute.shop` has no way to say which slot to show, and the Item Store sits below the balance, sound toggle and generator section, so it may open off-screen. It needs (1) a callback from `MergeBoardView` into the viewer, (2) a payload on the shop route (for example `case shop(focusSlot: UUID?)`, touching its three call sites and `id`), (3) a `ScrollViewReader`, row `.id`s and a highlight in `ShopView`/`DogTagStoreRow`, and (4) swapping one sheet for another through the same `.sheet(item:)` binding, which SwiftUI does by dismissing and re-presenting; it should work but must be checked on the Simulator. Most of this is view code with no unit test. Roughly one session plus a Simulator pass, against Option A's one session.

**What the references show (Triage §2.10, owner's R1 recording, 18 Nov 2026).** Travel Town sells **single items for gems**: its chain viewers carry a green SEE IN STORE button and put a gem price **on the tier row** for any tier the store is selling now (Peas viewer: 16 gems on the leek tier; Mushroom Home viewer: 5 and 153 gems), and its store lists single items at 2 to 153 gems in stock of 1 to 4, refreshing daily, with a 10-gem Refresh. The store screen appeared right after the viewer in the clip, but the recording shows no finger, so "the button opened the store" is inferred, not seen. Gossip Harbor's viewers in the same session showed **no prices at all** (version 4.12.1); a July reading (`PawSanctuary_Gap_Analysis.md`, from `Findings_26July.md`) recorded a SEE IN STORE button beside a 14-gem item there. **Travel Town's red-cart price on an order slot is still unknown**, and R1 found the cart is not on every missing slot (inferred: only on items the store sells). So:
- *Price on the tier row:* Travel Town does it. Both options here do it.
- *What the tap does:* not observed in either game. The label and the clip's order point to navigation.
- The two references do not clearly agree, so under D14's standing rule (§1: "where they disagree there is nothing to copy and the owner picks") the owner picks.

**Recommendation: Option A (direct buy, one tap, as in the shop).** Being honest about the difference from Q17: the reference evidence leans towards B, and if matching Travel Town's flow as closely as possible is what the owner wants, B is the right answer. A is recommended on other grounds: it is smaller and fully testable, it keeps the player on the screen where they chose the item, and under D14 that purchase now does what D3 promised. Two of Q17's reasons are weaker than they looked: B was costed as "one line" and is not, and A's accidental-spend risk is the same as the shop's own. Q17's D9 point stands for both options: neither changes price or stock.

**Both options satisfy D13's routing rule.** The first draft said navigation "would not use" `purchaseDogTagStoreSlot`. That was wrong: in Option B the player buys through `DogTagStoreRow`, which calls it (`ShopView.swift:345`).

### 3.2 What the player sees (Option A; the deltas for B are in §3.4)

Before the D7 gate: nothing new; no price anywhere in the viewer. After it: on a tier today's Item Store is selling, a small caption "In today's Item Store" and a tag-price button. Tap: the item appears on the board (or in storage if the board is full), the Dog Tags drop by exactly the price, the row changes to "Sold", the "×N" badge goes up by one, and the viewer stays open. If an order wanted that item and it landed on the board, the order card behind the sheet lights its slot (and shows Deliver if that was the last one); the viewer itself says nothing about orders.

### 3.3 Changes (Option A)

1. View-model helper `chainViewerStoreSlot(chainID:tier:) -> DogTagStoreSlot?`. Returns `nil` unless `isMonetizationUnlocked`. Otherwise returns the store's slot for that chain and tier: the **first unsold** match if there is one, else the first sold match (so the row says "Sold" rather than silently losing its button), else `nil`. More than one slot can match: `makeStock` picks a random chain per slot, and while the tier band is narrow (deepest tier 1 or 2) two or three slots share a tier (§8 item 4).
2. The viewer calls `viewModel.refreshDogTagStore()` on appear, **only when `isMonetizationUnlocked`**, so a day-old shelf is not shown and no stock is built before the gate.
3. A tier row with a slot shows the caption and a price button matching `DogTagStoreRow`: tag icon and price; greyed if `dogTags < priceDogTags`; "Sold" if `purchased`. Tapping calls `purchaseDogTagStoreSlot(slot)`. **That function is the only thing the button calls.**
4. If the purchase returns false (sold, unaffordable, or board and storage both full, which fires `.inventoryFull`), nothing changes and nothing is charged. No extra handling.
5. If the board was full when the player tapped (`boardState.boardIsFull`), and the purchase succeeds, the item went to storage. Show a one-line caption under the row: "Sent to storage, the board is full". This is the one case where the "×N" badge rises while an order wanting the item stays unlit (§2), so the player is told where it went.
6. The viewer stays open after a purchase; the owned badge is the confirmation.
7. Chains the store never stocks (supplies, materials, toolbox, sub-objects, currency, wildcard) never have a slot, so they show nothing. No special case.

**Copy rule (updated for D14).** The caption and button do not mention orders, "fill", "deliver" or "complete". The reason is no longer that a purchase cannot fill an order (under D14 it can); it is that the viewer does not know whether any order wants this item, a purchase never delivers by itself (the player still presses Deliver), and an item sent to storage does not count. The copy says where the item is sold and, after a full-board purchase, where it went; nothing about what it is for.

### 3.4 If the owner picks Option B instead

Steps 1, 2 and 7 stay. Replace 3 to 6 with: the row shows the price as a button; tapping sets the route to the shop focused on that slot's id (via a callback passed from `MergeBoardView` to the viewer); `ShopView` scrolls to the Item Store on appear and highlights the focused row for about two seconds; the purchase, its refusals and the full-board toast are then exactly the shop's. Step 5's storage caption would belong in `DogTagStoreRow` and apply to every shop purchase; that is a small, separate improvement and is not part of this task.

### 3.5 Done when

Before the D7 gate the viewer shows no price anywhere. After it, a stocked tier shows its price; a purchase puts the item on the board (or in storage, with the caption), debits the exact slot price once, flips the row to "Sold", moves the D6 spend counter as a shop purchase does, and, if an open order wanted that item and it landed on the board, that order's slot reads as held without anything being delivered or paid.

### 3.6 Tests (`ChainViewerStoreTests.swift`, new; build the view model as `OrderFulfilmentRuleTests.makeViewModel()` does, including `vm.boardState.recalc()`)

- The helper returns `nil` before the D7 gate and the slot after it (`unlockMonetizationForTesting()`, `MergeBoardViewModel.swift:1622`; tests build Debug).
- It returns `nil` for a chain/tier the store does not stock; the sold slot (not `nil`) after a purchase; and, with two slots for the same chain and tier, the unsold one first.
- Buying through the viewer's path debits once, marks the slot sold, and increments the spend counter (mirror the existing Dog Tag store case in `SpendQuotaDailiesTests.swift`).
- **D14 guard (replaces the first draft's D12 guard):** with an open order wanting the exact chain and tier and a free board cell, buying the slot the helper returns makes `orderHeldState(at: 0)?.isReady` true while `lines[0].fulfilled` stays 0 and the order is not claimed; with a full board the same purchase goes to storage, `ownedItemCounts` rises by one and the order is **not** held. `OrderFulfilmentRuleTests` (`:188`, `:202`) already pins this for `purchaseDogTagStoreSlot`; these tests tie the viewer's route to it, so a later "smart" shortcut cannot bypass that function or auto-deliver.
- Mutation-check each new test (break the thing it guards, see it fail, restore), as was done for the D12 and D14 tests.
- Option B keeps the helper tests and the D14 guard; the scroll and highlight are checked on the Simulator only.

## 4. Why Task 2.2 is worth doing at all

D13 gave two reasons: it is the contextual buy path the Parity Audit lists as partial (`Feature_Parity_Audit.md` row 39), and it serves D3's conversion reasoning, which the random daily shelf serves only loosely because it offers three random tiers whether or not they match anything the player wants. D14 strengthens the second reason: a bought item can now be the missing order slot. The viewer is the one place the player has already picked a specific item. Showing the store's price there does not change what the store sells (D9); it makes an existing offer findable where the player is looking. With the order-slot cart held back (Q18 c), it is also the only such path in the first build.

## 5. Task 2.3 — "Made by" line: go/no-go

**Verdict: GO.** A chain-to-producer display name can be had from data that already exists, with no new table and no save change. The lookup is one small function (about fifteen lines).

### 5.1 What generates each chain (from code)

| Chain category | Generated by | Evidence | Name available |
|---|---|---|---|
| `animal.<species>` (15 chains) | That species' **family spawner**. The spawner's species picks the chain: `ContentRegistry.animalChainID(species)` | `MergeBoardViewModel.swift:1781-1790`; `ProducerTile.species` / `animalChainID`, `AnimalSpecies.swift:537`, `:629` | `AnimalSpecies.spawnerName` (`AnimalSpecies.swift:85-103`), e.g. "Scratching Post"; already shown in the info bar (`MergeBoardViewModel.swift:712-713`). Species from the chain id by the same parse `MergeChain.artImage` uses (`ItemChain.swift:81`). |
| `subobject.<species>` (15 chains) | The **same family spawner**, as its ~20% sub-object drop | `SubObjectSystem.swift:123-124` (`"subobject.\(species.rawValue)"`) | Same `spawnerName`; species parsed as at `ItemChain.swift:84`. |
| `supply.grooming` / `supply.food` / `supply.shelter` | **Grooming Box / Feed Station / Supply Crate**, one each, tier 0 | `ProducerLevel.targetChainID`, `AnimalSpecies.swift:454-460`; spawn at `MergeBoardViewModel.swift:1897-1898` | `ProducerLevel.displayName` (`AnimalSpecies.swift:416-424`). Reverse lookup: `ProducerLevel.allCases.first { $0.targetChainID == chainID }`. |
| `currency.kibble` / `currency.coin` | **Every** family spawner (a small currency drop), plus the kibble caches seeded under locked rows | `SubObjectSystem.swift:126-129`; `MergeBoardViewModel.swift:1158` | No single producer: show nothing. |
| `material.*` | Not a board item from a producer; materials go straight to the Materials tab | `InventoryStore.swift:123-125` | Show nothing. |
| `tool.toolbox`, `wildcard.wildcard`, `superpower.<species>`, `parallelboard.secondchances` | Rewards, Dog Tag purchase, superpower activation, Parallel Board only | `ItemChain.swift:226-251` (ids and comments) | Show nothing. |

Not a generator for this purpose: the legacy `rescueCrate` / `shelterPod` / `fosterHome` producers emit a **random** animal chain (`MergeBoardViewModel.swift:1866-1892`). They are superseded by family spawners and survive only on old saves; the line names the family spawner.

### 5.2 The lookup to use

Add to `MergeChain` (`ItemChain.swift`), next to `artImage(forTier:)`, which already does the same species parse:

```swift
/// Display name of the producer that makes this chain, for the chain viewer's
/// "Made by" line (Spec_ChainViewerUpgrades_Draft.md §5). nil when no single
/// producer makes it (currency, materials, rewards, bought items).
var producerDisplayName: String? {
    switch category {
    case .animal:
        return AnimalSpecies(rawValue: id.replacingOccurrences(of: "animal.", with: ""))?.spawnerName
    case .subObject:
        return AnimalSpecies(rawValue: id.replacingOccurrences(of: "subobject.", with: ""))?.spawnerName
    case .supply:
        return ProducerLevel.allCases.first { $0.targetChainID == id }?.displayName
    default:
        return nil
    }
}
```

`parallelboard.secondchances` is registered as `.animal` (`ItemChain.swift:72-80`) but its id does not parse as a species, so it correctly returns `nil` with no special case.

### 5.3 How it shows, and its one honest limit

Only an item a producer emits is *generated*; higher tiers are reached by merging, and a family spawner can emit above tier 0 (Alignment Plan Phase 2 item 2.3, generator-tier progression; in code the tap tier comes from the spawn multiplier, `MergeBoardViewModel.swift:1794`, plus the high-tier drop and Hibernate, `:1806-1819`). The reference's footer is per item, and how it treats a merged tier was not captured. So show the line **once per chain, under the title**, as "Made by: <producer>", not per tier. Chains with `nil` show nothing. The line names the producer even if the player does not currently have one on the board (supply producers are finite, `maxCharges` 6, `AnimalSpecies.swift:491`); that is still true of where the item comes from.

### 5.4 Done when, and tests

Done when an animal chain, a sub-object chain and a supply chain each show the right producer; currency, material, toolbox and wildcard chains show no line; no table was added and nothing is persisted.

Tests (`ChainViewerProducerNameTests.swift`, new, pure, no view model): every `AnimalSpecies` maps its animal chain and its sub-object chain to its `spawnerName`; each of the three supply chains maps to its box's `displayName`; `currency.kibble`, `material.wood`, `tool.toolbox`, `wildcard.wildcard` and `parallelboard.secondchances` give `nil`. Mutation-check one case.

## 8. Where the spec and the code disagree

Found while re-reading on 22 Nov 2026. None is fixed here; this is a document change.

1. **The first draft's D12 rule is gone from the code.** It said a bought item does not credit an order and required a test that "buying leaves the order uncredited". Under D14 (tasks 1.3–1.5, merged) a purchase on the board makes the slot held (`AnimalSpecies.swift:1152-1166`; `OrderFulfilmentRuleTests.swift:188`). Corrected throughout this spec.
