## 0. What this is, and what it is not

**In plain language.** Tapping the small "i" next to an item's name opens a list of every step of that item's chain. Since PR #115 the list also shows how many of each step you have (a small "×2" badge). This spec adds two more things: on a step that today's Item Store is selling, its price and a **See in store** button that closes the list and opens the shop with that item in view (you buy there, with one more tap, exactly as today); and one line saying which spawner makes the chain ("Made by: Scratching Post").

**What changed since the first draft.** When this spec was first written, a bought item could never fill an order (D12). Under **D14** it can: if you buy an item an order wants, and it lands on the board, that order's slot lights up, and once every slot is lit the **Deliver** button appears. The shortcut is therefore now a real way to reach the item you are one short of, which is the reason D3 gave for selling items at all. The owner then answered CV-1 (§3.1): the shortcut **navigates**, it does not buy.

All three additions are derived live; **none is persisted**. **No save change**: no new persisted field, so no schema bump, migration or `PersistenceTests` case (CLAUDE.md rule 4 is not triggered). The shop focus travels in the sheet route, which is view state and never saved. If a task turns out to need persisted state, stop: that is the held first-discovery collection (D13 part 1) and is out of scope.

## 3. Task 2.2 — "See in store" shortcut

### 3.1 Owner decision CV-1: answered B, 22 Nov 2026

**CV-1 answered B, 22 Nov 2026 (owner):** tapping "See in store" **opens the shop scrolled to that item**; the player buys there with one more tap, through the shop's existing row. It does **not** buy from the viewer.

**Reason.** The only reference evidence for this button is a July note: Gossip Harbor showed a "SEE IN STORE" button beside a visible 14-gem price on a chain-viewer tier (`Findings_26July.md` line 98, outside the repo, in the folder above it; carried into `Merge2_Reference_Blueprint.md` line 199). What the tap did was **never observed**: the recordings do not show a finger, and Travel Town's R1 clip shows the store after the viewer, which is inferred, not seen (`Triage_ModelOnReferences.md` §2.10). B matches the label; it goes through the existing purchase path by construction (D13), because the only buy button stays `DogTagStoreRow`; and it is gentler under D9, since the player sees the whole store and the price again before spending anything.

**Not yet confirmed by a recording.** Recording request **R12** (`Recording_Guide.md`, optional) taps the button once in Gossip Harbor. If it turns out to buy on tap, the owner may switch to the direct buy (former option A). That is a small change to this design: the "See in store" button would call `purchaseDogTagStoreSlot` with the live slot instead of the navigation callback; the helper in §3.3 step 1 and the D14 tests stay.

**History.** Raised first as **Q17** in `PROJECT_STATE.md`, where the project manager recommended navigation (Q17's labels are the other way round: its (a) is navigation, its (b) the direct buy). Restated in this spec on 22 Nov 2026 as CV-1 with options A (direct buy, which this spec then recommended) and B (navigation). The owner chose B. The direct-buy design and its costing are in git history of this file (PR #137, commit `0143cec`) and are not carried forward.

### 3.2 What the player sees

**Before the D7 gate:** nothing new; no price and no button anywhere in the viewer.

**After the gate**, on a tier today's Item Store is selling and has not sold:
- Under the tier name, a caption **"In today's Item Store"** and the price as a **label** (tag icon and number, plain text, the same tag glyph as `DogTagStoreRow`). The label is not tappable and is not styled as a button.
- A small **"See in store"** button on the row.
- Tapping it: the viewer sheet closes, the shop sheet opens, the shop scrolls so that slot's row is in view, and the row is highlighted for about two seconds. The player buys there with one tap on the row's price button, exactly as today (refusals, the full-inventory toast and the D6 spend counter are the shop's, unchanged).
- After buying, closing the shop returns to the board, not to the viewer. If an order wanted that item and it landed on the board, the order's slot is lit (and Deliver shows if it was the last one); the player still presses **Deliver**. If the board was full, the item went to storage and the order is **not** lit (§3.6).

On a tier the store is not selling, on a tier whose only matching slot is sold, and on every chain the store never stocks (supplies, materials, toolbox, sub-objects, currency, wildcard): nothing new.

### 3.3 Changes

1. **View-model helper** `chainViewerStoreSlot(chainID: ChainID, tier: Int) -> DogTagStoreSlot?` on `MergeBoardViewModel`, next to `purchaseDogTagStoreSlot` (`MergeBoardViewModel.swift:1956`). Returns `nil` unless `isMonetizationUnlocked`. Otherwise returns the **first unsold** slot in `dogTagStore.slots` whose `chainID` and `tier` match, else `nil`. More than one slot can match (§8 item 4): `makeStock` picks a random chain per slot with replacement, and while the tier band is narrow two or three slots share a tier. A sold slot returns `nil`, so its row loses the price and button rather than showing a dead "Sold".
2. **View-model helper** `liveDogTagStoreSlot(id: UUID) -> DogTagStoreSlot?`: the slot with that id in `dogTagStore.slots` if it exists **and is unsold**, else `nil`. Used by the shop on appear (step 7), so it never scrolls to or highlights a slot that has since been sold or replaced.
3. **Fresh shelf.** The viewer calls `viewModel.refreshDogTagStore()` in `.onAppear`, **only when `isMonetizationUnlocked`**, so a day-old shelf is not shown and no stock is built before the gate. (`rotateIfNeeded` is idempotent and cheap, `DogTagStore.swift:28-35`.)
4. **Viewer row.** `MergeProgressionView` (`MergeBoardView.swift:1772`) gains `var onSeeInStore: (UUID) -> Void`. Inside the `ForEach` (`:1784`, next to the `ownedCount` read at `:1785`), each row reads `viewModel.chainViewerStoreSlot(chainID: chainID, tier: index)`; when non-nil, it shows the caption, the price label and the "See in store" button. The button's action is only `onSeeInStore(slot.id)`; whether that id is still live is checked once, by the shop on appear (step 7), after the shop's own stock refresh. **The viewer never holds a buy action and never calls `purchaseDogTagStoreSlot`.** It passes only a slot id, never a `DogTagStoreSlot` value. Accessibility: the row's combined label gains "in today's Item Store for N Dog Tags"; the button is its own element, "See in store".
5. **Route payload.** `SheetRoute.shop` becomes `case shop(focusSlot: UUID?)` (`MergeBoardView.swift:1749`). Its `id` stays the constant `"shop"` (`:1758`; the pattern `case .shop:` still matches with a payload). The two existing call sites become `activeRoute = .shop(focusSlot: nil)` (`:662` HUD cart, `:712` `onOpenShop`); `routeContent` becomes `case .shop(let focus): ShopView(storeManager: storeManager, viewModel: viewModel, focusSlotID: focus)` (`:785-786`). `Equatable` stays synthesised. Nothing persists the route.
6. **Viewer to shop.** `routeContent`'s `.mergeProgression(let chainID)` case (`:825-826`) passes `onSeeInStore: { id in activeRoute = .shop(focusSlot: id) }`. Because the new route has a different `id` (`"shop"` vs `"progression-…"`), SwiftUI's `.sheet(item:)` (`:349`) **dismisses the viewer and then presents the shop**; nothing else is needed. This must be checked on the Simulator (§6). **Fallback if the swap misbehaves** (shop does not appear, or appears and is immediately dismissed): add `@State private var pendingShopFocus: UUID??` (or a small wrapper) to `MergeBoardView`; the callback sets `pendingShopFocus = id` and `activeRoute = nil`; the existing `.sheet(item:)` gains `onDismiss: { if let f = pendingShopFocus { pendingShopFocus = nil; activeRoute = .shop(focusSlot: f) } }`. That onDismiss fires for every route but does nothing when nothing is pending. The tutorial's `.onChange(of: activeRoute)` (`:110-114`) is unaffected either way.
7. **Shop scroll and highlight.** `ShopView` gains `var focusSlotID: UUID? = nil` (default keeps its one call site compiling) and `@State private var highlightedSlotID: UUID?`. Wrap the `ScrollView` (`ShopView.swift:20`) in `ScrollViewReader { proxy in … }`. Give each Item Store row an explicit `.id(slot.id)` in the `ForEach` (`:279-281`). Pass `highlightedSlotID` into `DogTagStoreSection` (new parameter, default `nil`) and on to `DogTagStoreRow` as `isHighlighted: Bool = false`, drawn as a coloured stroke on the row's rounded background (`:364-366`). On appear (`.task` on the `ScrollView` content): call `viewModel.refreshDogTagStore()` first, so a day rollover is applied before the check (it is the same idempotent call `DogTagStoreSection` already makes, `:286`); then `guard let id = focusSlotID, viewModel.liveDogTagStoreSlot(id: id) != nil else { return }`; wait for the sheet to finish presenting (start with about 0.35 s, tune on the Simulator); `withAnimation { proxy.scrollTo(id, anchor: .center) }` (no animation under Reduce Motion); set `highlightedSlotID = id`; clear it after about two seconds. If the guard fails, the shop opens at the top, unscrolled and unhighlighted, exactly as from the cart button.
8. **No other change to the shop.** The buy button, its disabled/greyed/"Sold" states, the reroll, and `purchaseDogTagStoreSlot` are untouched.

**Copy rule.** The caption, price label and button do not mention orders, "fill", "deliver" or "complete". The viewer does not know whether any order wants this item, a purchase never delivers by itself (the player still presses Deliver), and an item sent to storage does not count. The copy says where the item is sold and offers to go there; nothing about what it is for.

### 3.4 Stock or sale changes while the viewer is open

The rule: **the viewer never causes a stale buy, because it cannot buy at all.** At worst the button disappears, or the shop opens unscrolled.

- **Slot sells.** Only the shop row sells a slot, and the shop cannot be open at the same time as the viewer (one sheet at a time). If it did happen, `DogTagStore` is `@Observable`, so the row re-renders, `chainViewerStoreSlot` returns `nil` (or the other unsold duplicate) and the button hides.
- **Paid refresh.** Only reachable from the shop; same as above. If stock were rebuilt while the viewer is open, the row re-renders against the new slots: the button disappears, or appears for a new slot with its own id.
- **Daily rollover while the viewer is open.** Nothing rebuilds the stock until `refreshDogTagStore()` is called (§1), so the viewer keeps showing yesterday's slot. Tapping it opens the shop; the shop's step-7 refresh rebuilds the stock with new ids, `liveDogTagStoreSlot` finds nothing, and the shop opens **unscrolled**, showing today's stock. Nothing is charged.
- **Purchase refused in the shop** (unaffordable, sold, or board and storage both full, which fires `.inventoryFull`): the shop's existing behaviour, nothing charged.

### 3.5 Orders (D14) after a purchase made through the shortcut

The purchase is an ordinary shop purchase, so the D14 rule applies unchanged:
- If the item lands **on the board** and an open order wants that chain and tier, the order's slot reads as held (`orderHeldState(at:)`, `MergeBoardViewModel.swift:3870`); once every slot is held, Deliver appears. **The player still presses Deliver** (`deliverOrder(id:)`, `:3913`); nothing is delivered, no `OrderLine.fulfilled` moves, no reward is paid, by the purchase itself.
- If the board was full, the item goes to **storage** and **does not count**: the order stays unlit until the player places the item on the board. The viewer's "×N" badge (board + storage) will still rise if the player reopens the viewer.

### 3.6 Known gap left alone: storage gives no notice in the shop

The superseded direct-buy design had a "Sent to storage, the board is full" caption in the viewer. Under B the purchase happens in the shop, whose row today says nothing when an item goes to storage (`placeOrBankItem` only toasts when storage is full too, `MergeBoardViewModel.swift:2194-2204`). So a player with a full board can buy the item an order wants and find the order still unlit. That is **existing shop behaviour**, not introduced here. A caption in `DogTagStoreRow` would cover every shop purchase; it is a small, separate improvement and is **not part of this task** (listed under Out of scope).

## 4. Why Task 2.2 is worth doing at all

D13 gave two reasons: it is the contextual path to a store item that the Parity Audit lists as partial (`Feature_Parity_Audit.md` row 39), and it serves D3's conversion reasoning, which the random daily shelf serves only loosely because it offers three random tiers whether or not they match anything the player wants. D14 strengthens the second reason: a bought item can now be the missing order slot. The viewer is the one place the player has already picked a specific item. Showing the store's price there and a way to it does not change what the store sells (D9); it makes an existing offer findable where the player is looking. With the order-slot cart held back (Q18 c), it is also the only such path in the first build.

### 5.2 The lookup to use

Add to `MergeChain` (`ItemChain.swift`), next to `artImage(forTier:)`, which already does the same species parse:

```swift
/// Display name of the producer that makes this chain, for the chain viewer's
/// "Made by" line (Spec_ChainViewerUpgrades_Draft.md §5). nil when no single
/// producer makes it (currency, materials, rewards, bought items).
var producerDisplayName: String? {
    switch category {
    case .animal:
        return AnimalSpecies(rawValue: id.replacingOccurrences(of: "animal.", with: ""))?.spawnerName
    case .subObject:
        return AnimalSpecies(rawValue: id.replacingOccurrences(of: "subobject.", with: ""))?.spawnerName
    case .supply:
        return ProducerLevel.allCases.first { $0.targetChainID == id }?.displayName
    default:
        return nil
    }
}
```

`parallelboard.secondchances` is registered as `.animal` (`ItemChain.swift:72-80`) but its id does not parse as a species, so it correctly returns `nil` with no special case.

### 5.3 How it shows, and its one honest limit

Only an item a producer emits is *generated*; higher tiers are reached by merging, and a family spawner can emit above tier 0 (Alignment Plan Phase 2 item 2.3, generator-tier progression; in code the tap tier comes from the spawn multiplier, `MergeBoardViewModel.swift:1794`, plus the high-tier drop and Hibernate, `:1806-1819`). The reference's footer is per item, and how it treats a merged tier was not captured. So show the line **once per chain, under the title**, as "Made by: <producer>", not per tier. Chains with `nil` show nothing. The line names the producer even if the player does not currently have one on the board (supply producers are finite, `maxCharges` 6, `AnimalSpecies.swift:491`); that is still true of where the item comes from.

## 8. Where the spec and the code disagree

Found while re-reading on 22 and 23 Nov 2026. None is fixed here; this is a document change.

1. **The first draft's D12 rule is gone from the code.** It said a bought item does not credit an order and required a test that "buying leaves the order uncredited". Under D14 (tasks 1.3–1.5, merged) a purchase on the board makes the slot held (`AnimalSpecies.swift:1152`; `OrderFulfilmentRuleTests.swift:188`). Corrected throughout this spec.
2. **`PawSanctuary_Alignment_Plan.md` D13 still says** "per D12 a bought item still does not fill an order directly". D14 supersedes it (D14 §4 says the opposite, correctly), but the D13 paragraph was not edited. Not changed here; flagged for whoever next edits the plan.
3. **The first draft's §1 listed "order credit" as a non-census definition of ownership.** Orders now read `boardTaskCensus`, and a fourth definition, `ownedItemCounts`, exists (`MergeBoardViewModel.swift:767`). The badge (board + storage) and the order rule (board only) can disagree on screen (§2).
4. **The store can stock the same chain and tier more than once.** `makeStock` picks a random chain per slot with replacement (`DogTagStore.swift:69`), and when the tier band is narrow the spread puts two or three slots on one tier (`:60-68`). §3.3 step 1 returns the first unsold match.
5. **A slot's price uses the unclamped tier.** `makeStock` clamps `tier` to the chain's `maxTier` but prices the unclamped value (`DogTagStore.swift:71-73`). Unreachable while the band tops out below every chain's top tier, so harmless; worth remembering for the fifteen-tier spec.
6. **"Navigation is a one-line change" (first draft §3) was wrong**: it needs a route payload, a callback into the viewer, a `ScrollViewReader` with row ids and a highlight in `ShopView`, and a sheet swap (§3.3 steps 4–7). **"Navigation would not use `purchaseDogTagStoreSlot`" was also wrong**: the shop row calls it (`ShopView.swift:345`).
7. **Task-number clash.** The first draft (and D13) cite "generator-tier progression (Task 2.3)"; that is the Alignment Plan's Phase 2 checklist item 2.3, not revision-plan task 2.3 (this spec's "Made by" line). The code's own comments number Phase 2 differently again (`PawSanctuary_Alignment_Plan.md` §5 note). Disambiguated in §5.3.
8. **`Spec_HeldItemOrders.md` §3.5 cites line numbers from `6d5a409`** (`isMonetizationUnlocked` `:396`, `purchaseDogTagStoreSlot` `:1894`); on `1f7ec66` they are `:400` and `:1956`. Expected drift, noted only so nobody chases the old numbers. Likewise `deliverOrder(id:)` moved from `:3856` (`de3e8b2`) to `:3913`.
9. **The July sources describe the reference button as a direct buy.** `Findings_26July.md` line 98 says items are bought "straight from the chain viewer" and `Merge2_Reference_Blueprint.md` line 199 says "purchasable … directly from the chain viewer", both beside the "SEE IN STORE" button. Neither recorded the tap; the wording is an interpretation of a still frame. CV-1 B follows the button's label instead. R12 (`Recording_Guide.md`) would settle it.
10. **`purchaseDogTagStoreSlot` trusts the slot value it is given.** It checks `slot.purchased` on the passed copy (`MergeBoardViewModel.swift:1957`) and `markPurchased` silently does nothing for an id no longer in stock (`DogTagStore.swift:90-93`), so a caller holding a stale slot from before a rebuild could buy an item the store no longer offers. Unreachable today (the only caller is `DogTagStoreRow` with live `ForEach` values) and kept unreachable by this design (the viewer passes only an id, the shop re-resolves it). Not fixed here; worth a guard if a second caller is ever added.
11. **Q17 and CV-1 use opposite letters.** In `PROJECT_STATE.md`, Q17 (a) is navigation and (b) the direct buy; in this spec CV-1 A was the direct buy and B navigation. The owner's answer is **CV-1 B = navigation = Q17 (a)**.
