## 1. Current state, measured today

`attemptMergeOrMove(from:to:)` is [MergeBoardViewModel.swift:1762–1905](../PawSanctuary/MergeBoardViewModel.swift#L1762) — **144 lines**, unchanged in size since the Phase A appendix scan (13 Aug), though its absolute line numbers have shifted with later Phase C commits. It is the **only** function in the file that touches all four board-state surfaces (`board[...]`, `boardIsFull`, `emptyUnlockedCells`, `recalcBoardIsFull()`) and it does so through **direct `board[...]` indexing exclusively** — it was explicitly excluded from every Phase C round, so none of the ten `BoardStateManager` primitives are used here yet.

It is not one merge path with options bolted on — it's five structurally distinct outcomes, gated by early returns and nested conditionals, not a shared pipeline:

| Outcome | Lines | What happens |
|---|---|---|
| **Producer merge/swap/move** | 1768–1795 | `srcProducer` present: same-level → upgrade one level (with a 600ms `animatingCell` pulse); different level → swap; empty destination → move. Own `recalcBoardIsFull()`, own early `return`. Explicitly commented as the one exception to the file's "always recalc after an occupancy change" rule (see the comment at 1788–1791) — a real, load-bearing bug-shaped subtlety, not incidental. |
| **Superpower piece spent** | 1801–1812 | `srcItem.chain?.category == .superpower` and a `dstItem` exists → delegates to `applySuperpowerMerge`, which returns a `Bool`. Skips score/XP/bubble/`checkSuperpowerUnlock` entirely — a deliberately separate pipeline from a normal merge. |
| **Wildcard/animal merge** | 1813–1899 | The big one. Eligibility check (wildcard adopts the other item's identity; same-chain-same-tier otherwise) → on success: score (with spotlight multiplier), XP, top-tier celebration *or* bubbling, `mergeCount`/`lastMergeTimestamp`/`lastMergedSpeciesRaw`, `recalcBoardIsFull()`, `updateAllAfterMerge` (→ tier-unlock check, quest/daily-challenge progress ×2 if Hedgehog superpower is active, order progress, spotlight reward payout), `checkSuperpowerUnlock`, `applyPassivePowers`, then **two more branches** for what happens to the merged tile itself: completed sub-object → maybe grants a superpower piece to inventory instead of leaving the tile; power-up-category or completed-sub-object → rolls rarity (if applicable) and moves the tile to power-up inventory. Ends with the 600ms animation pulse and captures `preMoveSnapshot` (Nine Lives undo) — captured **after** all these mutations, deliberately, since assigning it earlier would self-invalidate via `board`'s `didSet` (comment at 1828–1831). |
| **Ineligible pair** | 1896–1899 | Plain item swap, no side effects, no `recalcBoardIsFull()` (occupancy didn't change). |
| **Empty destination** | 1900–1904 | Plain move, `recalcBoardIsFull()`. |

**Side-effect surface reached from the merge branch alone:** `score`, `grantXP`, `mergeCount`, `lastMergeTimestamp`, `lastMergedSpeciesRaw`, `quests` (four distinct call sites across `updateAllAfterMerge`), `adoptionBoardCoordinator` (via `updateOrdersAfterMerge`), `kibbleEngine` (spotlight reward payout), `deepestUnlockedTier`/`checkTierUnlock()`, `unlockedSuperpowerSpecies`/`showSuperpowerUnlockBanner`, `inventoryStore` (power-up/superpower-piece routing), `SoundManager`, `HapticManager`, `enqueueToast`, `animatingCell`, `preMoveSnapshot`. This is not a board-mutation function that happens to also touch a few other things — board mutation is a minority of what it does.

**Zero test coverage.** Confirmed again while writing this doc — `PawSanctuaryTests/` has no `BoardStateManagerTests.swift` (flagged as worth writing in the Phase B entry, never done) and nothing exercises `attemptMergeOrMove` directly. Every verification of merge behavior across Phases B/C was live-simulator testing, never automated.

## 2. Why this needs its own resolution pass, not just "apply the Phase C pattern"

Phase C's primitive-routing pattern (swap `board[pos.row][pos.col].x` for `boardState.x(at: pos)`) doesn't fit here, and applying it directly would be a distraction. The point of `MergeResult` is that this function stops *performing* mutations and side effects inline and instead **computes and returns a description of what should happen**, which something else applies. If that redesign happens, routing the interim direct-`board[...]` reads through primitives first is churn that gets thrown away, not a stepping stone — worth deciding explicitly rather than defaulting into it.

The five-branch shape in §1 also means "rewrite `attemptMergeOrMove`" undersells the task. A `MergeResult` type needs to represent producer upgrades, producer swaps, producer moves, superpower-piece consumption, animal merges (with two further sub-outcomes for where the merged tile ends up), item swaps, and plain moves — seven-ish shapes, not one.

## 3. Open design questions

Two of the six questions below are now **resolved** (15 Aug 2026) — recorded here with rationale rather than left as options, since this doc's job is to be a decision record, not just a list of forks. The other four remain open. Four are genuine decisions this doc isn't the place to unilaterally settle without discussion — the two resolved below turned out to have a forcing fact behind them rather than being purely a matter of taste.

**A forcing fact that shaped both resolutions:** `applyPassivePowers` ([MergeBoardViewModel.swift:2569](../PawSanctuary/MergeBoardViewModel.swift#L2569)) is not deterministic. Fetch!/Multiply/Antler Drop all call `placeFreeTile` ([:2555](../PawSanctuary/MergeBoardViewModel.swift#L2555)), which places an item on `emptyUnlockedCells.randomElement()` — a random cell chosen from the board **as it exists after the primary merge write**, since `recalcBoardIsFull()` has already run by the time `applyPassivePowers` is called. Antler Drop additionally rolls `Int.random(in: 0..<4)`. A "pure `computeMergeResult` → inert data → `apply` just writes it" design (the framing §1/§4 originally implied) is therefore not achievable for the full merge outcome — the passive-power tail depends on post-primary-mutation board state and on randomness, not on anything a pre-mutation compute step could know in advance.

**A second instance of the same fact, found while writing D0's tests:** `maybeBubbleMergedItem` also rolls `Double.random(in: 0..<1) < bubbleChance` (0.15) *after* confirming order/quest eligibility — eligibility is necessary but not sufficient, matching the shape of the passive-power finding above. §1's branch inventory didn't call this out explicitly; it should be read as covered by "maybe bubbles" wherever it appears. This reinforces §3.1's resolution rather than changing it: `computeMergeOutcome` should decide *eligibility* (deterministic, testable), and the actual random roll — like `applyPassivePowers`'s — stays in `apply(_:)`'s procedural tail.

1. **RESOLVED — `MergeResult`'s shape.** Not one monolithic literal-data type. A two-layer split:
   - A pure, testable `computeMergeOutcome(from:to:) -> MergeOutcome?` decides only what's actually deterministic given `from`/`to` and the current board: eligibility (wildcard-adopts-identity vs. same-chain-same-tier), the resulting `chainID`/tier, score delta (with spotlight multiplier), XP delta, whether it's a top-tier completion vs. a bubble candidate, and the merged species. This is the real testable surface, and what D0's characterization tests should target first.
   - `MergeResult` stays a thin `enum`, one case per row of §1's table, carrying only what the deterministic step produced:
     ```swift
     enum MergeResult {
         case producerUpgrade(from: GridPosition, to: GridPosition, newLevel: ProducerLevel)
         case producerSwap(from: GridPosition, to: GridPosition)
         case producerMove(from: GridPosition, to: GridPosition)
         case superpowerPieceSpent(from: GridPosition, at: GridPosition)
         case merge(MergeOutcome)
         case itemSwap(from: GridPosition, to: GridPosition)
         case itemMove(from: GridPosition, to: GridPosition)
         case noOp
     }
     ```
   - `apply(_ result: MergeResult)` stays procedural for the cascade — `updateAllAfterMerge`, `checkSuperpowerUnlock`, `applyPassivePowers`, and the sub-object/power-up completion routing keep running as imperative calls, exactly as today, just centralized under one dispatch point instead of inlined in `attemptMergeOrMove`. This correctly scopes "compute" to the part that's genuinely computable rather than forcing randomized game logic into a data model it doesn't fit — the win is `attemptMergeOrMove` shrinking to "compute, then dispatch" and the eligibility/outcome logic becoming independently testable, not that every last effect becomes inert data.
2. **RESOLVED (implemented in D2's producer-branch step, refined in the merge-branch step, 15 Aug 2026) — dispatch location.** `apply(_ result: MergeResult)` on `MergeBoardViewModel`, as leaned toward — mirroring `apply(_ s: GameState)`'s existing naming (Swift resolves the overload by parameter type, no naming collision). Lives in `MergeBoardViewModel.swift` itself, right after `attemptMergeOrMove`, not in `MergeResult.swift` — applying a result is genuine stateful ViewModel work, not pure logic, so it stays with the rest of the ViewModel's mutation code rather than living alongside the pure compute functions. **The one-shared-switch-statement model didn't survive contact with the merge branch, as flagged here as a risk before it was built:** `.merge(MergeOutcome)`'s effect cascade has completely different tail semantics from the four producer cases (internal recalcs at specific points instead of one at the end, `selectedCell` never touched), so `apply(_:)` now dispatches to two separate private methods — `finishProducerAction()` for the producer cases' shared tail, `applyMergeOutcome(_:)` as `.merge`'s fully self-contained handler — rather than one switch with one tail after it. The per-sub-coordinator `handle(_:)` alternative still wasn't pursued; the two-method split solved the actual problem without it.
3. **RESOLVED — the Nine Lives snapshot's timing.** The current placement (assigned at the *end* of the merge branch, from values captured at the *start*) exists specifically to dodge `board`'s `didSet`-triggered invalidation, and that constraint is unchanged by the compute/apply split — if anything it gets cleaner to reason about:
   - Capture `preMergeBoard`/`preMergeInventory` **inside `apply(_:)`**, at the top of the `.merge` case, before any write — not inside `computeMergeOutcome`. Snapshot data isn't core merge-outcome data, so it doesn't belong in `MergeOutcome`'s payload; keeping it out also keeps `computeMergeOutcome` genuinely pure (no need to thread board-copy plumbing through a function whose job is just "decide what happens").
   - Assign `self.preMoveSnapshot` as the **literal last statement** of the `.merge` case's handling in `apply(_:)` — after the primary write, the `updateAllAfterMerge`/`checkSuperpowerUnlock` cascade, *and* `applyPassivePowers`'s own board writes. Same ordering guarantee as today (comment at [:1828–1831](../PawSanctuary/MergeBoardViewModel.swift#L1828)), just relocated one level up into `apply(_:)`.
   - Scope stays exactly as narrow as today: only `.merge` does this capture-then-assign dance. Producer moves, swaps, plain moves, and superpower-piece spends don't touch `preMoveSnapshot` currently and shouldn't gain that behavior as an accidental side effect of the rewrite.
4. **Async UI timing isn't result data.** Still open — and now live in production code, not just inline logic, since the merge branch's cutover. The 600ms `animatingCell` pulse (`Task { try? await Task.sleep(...); self.animatingCell = nil }`) appears **three** times once `placeFreeTile` is counted (producer upgrade, `applyMergeOutcome`'s own pulse, and every `placeFreeTile` call inside `applyPassivePowers`, which `applyMergeOutcome` calls before setting its own `animatingCell = outcome.to`) — and since `animatingCell` is a single property, a passive-power trigger firing `placeFreeTile` will clobber whichever cell the primary merge's own pulse was pointing at, and `applyMergeOutcome`'s own later assignment (`animatingCell = outcome.to`, which runs *after* `applyPassivePowers` in the ported order) will in turn clobber a passive-power tile's pulse. Confirmed still exactly reproduced by the port — verbatim ordering, not something this refactor changed. Still worth deciding whether Phase D leaves it as-is (matching today's actual, slightly-glitchy behavior) or fixes it as a small deliberate scope addition — not as an accidental side effect of restructuring the dispatch.
5. **RESOLVED for the producer and merge branches (D2, 15 Aug 2026); the general question stays open for superpower/swap/move.** §1 flagged that the producer branch's `recalcBoardIsFull()` timing is deliberately *not* "always recalc" — it's there so a later spawn can overwrite a producer the player just placed. `apply(_:)`'s producer cases preserve this exactly via a shared `finishProducerAction()` helper (`recalcBoardIsFull()` + `selectedCell = nil`, including for `.producerBlocked` — the case formerly named `.noOp`, renamed while wiring up the merge branch; see §3.1's entry below) — ported verbatim, not just conceptually. The merge branch's own ordering (multiple internal `recalcBoardIsFull()` calls at specific points, `selectedCell` never touched at all) is different enough from the producer tail that trying to force both through one shared post-switch tail would itself have been a bug — caught and fixed by splitting `apply(_:)` into `finishProducerAction()` and a separate `applyMergeOutcome(_:)` before either shipped, not after. D0's `testProducerOntoItemOccupiedCellIsNoOp` plus all of D0's merge-specific tests are what confirmed both held after their respective cutovers. Still open for superpower-piece-spent, the ineligible-swap fallback, and the empty-move branch.
6. **RESOLVED (implemented in D1, 15 Aug 2026) — `computeMergeOutcome`'s parameters.** Explicit parameters, as leaned toward: `computeMergeOutcome(from:to:srcItem:dstItem:spotlightChainID:spotlightMultiplierBonus:orders:urgentOrder:activeQuests:) -> MergeOutcome?`, a free function in `MergeOutcome.swift`, not a `MergeBoardViewModel` method. `ContentRegistry.shared` remains an implicit dependency, same as every other pure helper in this codebase (`isBubbleEligibleForQuestOrOrder`, `spawnCost(forTier:)`) — it's read-only content data, not mutable app state, so it doesn't need threading through. 19 tests in `MergeOutcomeTests.swift` exercise it with zero `MergeBoardViewModel` instantiation, confirming the testability payoff is real — plus two tests that cross-check its output against what `attemptMergeOrMove` actually produces on a live ViewModel, for direct confidence the extraction is faithful rather than just self-consistent.
